## 前置知识

### 为什么需要 BEV？

**BEV（Bird's Eye View，鸟瞰图）** 可以理解为：把摄像头看到的世界，转换成一张**从上往下看的地图**。

普通摄像头拍到的是透视画面——近处大、远处小——很难直接判断物体之间的真实位置。BEV 会利用相机的**标定信息**，把路面上的内容统一投影到同一个平面上，让车辆、行人、障碍物都像出现在地图上一样。这样不仅人看起来更直观，机器也更容易计算距离、判断相对位置和规划运动路线。

所以无论是汽车的 360° 环视、自动泊车，还是机器人的环境感知，BEV 的核心作用都是：把「看到的图像」变成「可理解的空间地图」。

### 摄像头标定

标定，就是让计算机知道「这个摄像头是怎么拍世界的」。

在 BEV 里，我们希望把画面准确地投影到地面上。如果没有标定，计算机只看到一张普通图片，它并不知道：

- 镜头有多广（焦距是多少）
- 图像中心在哪里
- 鱼眼镜头弯曲了多少（畸变）
- 摄像头安装在什么位置、朝向哪个方向

因此无法判断「图像中的这个像素，对应现实世界中的哪个位置」。

举个例子：你用一张纸画了 1 m × 1 m 的方格，用鱼眼摄像头去拍。由于透视和畸变，纸上的正方形在图像里会变成弯曲、大小不一的形状。标定的作用，就是建立 **像素 ↔ 真实世界** 的对应关系。

在环视 / BEV 中通常需要两类标定：

| 类型 | 解决什么 | 本项目对应 |
|------|----------|------------|
| **内参** | 摄像头本身的成像特性（焦距、主点、畸变）→ 去掉鱼眼变形 | Web 步骤 1 / `calibrate_intrinsics` |
| **外参** | 相对车体/世界的位置与姿态 → 把多路统一到同一地面坐标系 | Web 步骤 2；用单应式 **H** 把去畸变图映到鸟瞰画布 |

只有完成这两步，才能把前、后、左、右四路正确地「摊平」到地面并拼接。否则就会出现车道线对不齐、物体漂移、接缝明显等问题。

### BEV vs AVM

- **BEV**：偏「空间理解」——多路画面统一到同一坐标系，便于算位置与距离。  
- **AVM（Around View Monitor）**：偏「给人看的 360° 环视」——在 BEV 几何之上做拼接、融合、展示。  

可以记：**BEV 负责理解空间，AVM 负责展示空间**；现代汽车环视大多建立在 BEV 几何之上。本项目同时覆盖「标定出 BEV 几何」和「GPU 实时拼出环视画面」。

## 流程（概览）

```text
硬件就绪 / 开流探针
        ↓
   ① 内参标定（逐路鱼眼 → K, D）
        ↓
   ② 外参标定（十字架摆板 → 每路 H）
        ↓
   ②b 接缝精修（可选：重叠区共视板微调从路 H）
        ↓
   ③ 去畸变预览 / ④ 实时 BEV（GPU remap + warp + blend）
        ↓
   WebRTC 浏览器观看 / Docker 开箱部署
```

热路径原则：**角点求解在 CPU，实时去畸变与拼接在 GPU**；检测不得堵死推流循环。

## Step by Step

### 0. 环境与开流

```bash
cd ~/bev_demo/avm_gpu
source scripts/env_opencv_cuda.sh
./scripts/run_web.sh --host 0.0.0.0 --port 8787
# 浏览器 http://<板子IP>:8787/
```

Docker（JP7.2）：见 `docs/DOCKER.md`。注意 CSI 不能只挂 `/dev/video*`，还要 `media0`、`capture-vi-channel*` 等（否则能 open、不能 read）。

状态页先做 **Probe cameras**：四路应显示实际分辨率（常见 1920×1536）。

### 1. 内参

- 每路依次对着棋盘多姿态抓拍（张数见配置 `intrinsics_min/target`）  
- 结果写入 `calib_results/{front,back,left,right}.json`（含 `K`、`D`、`image_size`）  
- 改采集分辨率后旧内参可能失效，需重标  

### 2. 外参

- 用十字架把四块板摆在车体四周（约 90° 分隔，水平、近地）  
- 卷尺量 **板近边到车体中心** 的距离 → 填 `near_m`（误差会直接变成接缝误差）  
- Web 默认**逐路**自动锁定：当前路稳定检出 → 连拍求 H → 下一方向  
- 结果：`calib_results/extrinsics.json`  

### 2b. 接缝精修（推荐）

- 卷尺摆位很难毫米级准，接缝处常有错位  
- 在两路重叠区放**同一块**板，锁定参考路 H，只重解从路 H  
- 顺序：`front+left` → `front+right` → `back+left` → `back+right`  
- 两路需**同时、同步**认出同一块板（UI 上 `SYNC n/need`）  

### 3 / 4. 预览与 BEV

- 去畸变预览检查 FOV / balance  
- 实时 BEV 检查四路拼接与车体中心黑区（中心无纹理属正常 FOV 空洞，不是「画了个黑车」）

## 易错点（现场最容易翻车）

### 1. 棋盘「转了 180°」——RMS 完全看不出来

规则棋盘（尤其偶数格）存在 **180° 翻转歧义**：角点顺序颠倒后，重投影 **RMS 可以一模一样**，旧逻辑会「随便挑一个」，真值测试里曾出现约 **5 m 量级** 的方向错误。

**本仓做法**：用长短边先排除 **90° 错解**（8×6 非方形板）；再用「近边在图像里更长」在两个 180° 解里定向；并加光心投影方向安全网。

操作上：十字架四向板尽量朝向一致、贴地摆正；若 BEV 某一侧「整块翻面/镜像感」，优先怀疑 180° 歧义而非单纯 `near_m`。

### 2. 四路「差了约 90°」——侧视相机 QC 曾被误杀

left/right 的图像水平轴映射到 BEV 后接近竖直。若用「BEV 位移的 x 分量」做质检，侧视会**结构性接近 0**，被误判「病态」，其实 H 正常。

**本仓做法**：跨度改看**位移模长**，对称性改比**主奇异值**，与坐标轴朝向无关。

摆位上：十字架保证四向约 **90°**；`front/back/left/right` 与 `/dev/video*` 映射不要接反（见 `camera_profile.json`）。

### 3. 在「去畸变图」上找棋盘

去畸变会裁视野、边缘拉伸，远处小格子更容易丢。应在**鱼眼原图**检测，再把角点映射到去畸变坐标系求 H；且要求**整板角点都落在去畸变图内**，否则是假阳性（只瞥到邻路板边）。

### 4. 远距「看得见、认不出」

小预览图上找角点不够；全分辨率检测又不能塞进推流循环（曾把帧率打到 ~0.3）。现用后台线程 + SB 检测器兼顾远距与帧率。

### 5. 接缝精修左右不同步

两路各自累计 READY，板一挪就会「一边粘旧角点、一边还在找」。必须**联合同步计数**；四对都完成后要停自动连拍，否则画面会周期性卡住。

### 6. Docker / CSI

- JP7 没有现成的 `l4t-jetpack:r39` 大包镜像 → 用 `ubuntu:24.04` + 侧装 OpenCV 打进镜像  
- nvidia runtime **不带** CUDA toolkit 的 `libnpp*` 等 → 构建时 stage 依赖  
- 只映射 `video0..3` → 能 open、read 超时 → 补挂 VI / media 节点

## 目前效果

- **本机 / 容器**：四路开流探针通过；CUDA OpenCV 热路径实时去畸变与 BEV 拼接（WebRTC）  
- **标定闭环**：Web 引导完成内参 → 外参 →（可选）接缝精修 → 鸟瞰预览  
- **工程化**：分辨率与设备可配置；状态报告与日志分区；JP7.2 Docker 可构建推送（如 `leucushc/avm-gpu:0.2.0`）  
- **已知上限**：接缝仍受卷尺摆位与棋盘歧义影响；精修可改善，不宣称「零缝自动完美」

## 后续：加入 VLM

在 AVM / BEV「看得见周围」的基础上，可叠加视觉语言模型做场景理解、提示与交互，例如 [VILA](https://github.com/NVlabs/VILA)：

- 输入：环视关键帧或 BEV 相关裁剪  
- 输出：障碍物/停车位/施工区等自然语言或结构化标签  
- 与 Alpamayo 一类「端到端/具身智能」叙事衔接：几何层（本项目）+ 语义层（VLM）

本阶段交付重心仍是 **几何标定与实时环视**；VLM 作为下一阶段增强，不阻塞当前 AVM 部署。
